# SHM і передавання медіаконтракту

`converter.node_sdk` передає raw video й аудіо через локальні `mmap`-кільця. Runtime маршрутизує лише метадані через успадковані Unix sockets. Публікація прив’язана до ID воркера, порту, ревізії та нового UUID покоління. Runtime перевіряє власника порту, схеми, межі виділення, заголовки та права файлів. Вказівники процесної пам’яті й довільні шляхи між нодами не передаються.

У штатній інсталяції каталоги кілець створюються під `/run/ip-media-tool/` на tmpfs. Кожен воркер має окремий каталог. Linux-сценарій використовує приватний каталог під `/dev/shm`. Розмір одного кадру обмежений 32 MiB, покоління — 128 MiB, одночасні відкриті покоління одного воркера — 256 MiB. Сторінки резервуються при створенні. Вичерпання tmpfs може відхилити запуск нового покоління.

Кожен читач має незалежний курсор і відкриває кільця тільки для читання. Дані копіюються під коротким неблокувальним `flock`. Повільний споживач пропускає перезаписані слоти й отримує ознаку `DISCONT`. Якщо саме в момент запису читач копіює слот, джерело пропускає кадр замість очікування й позначає наступний успішний кадр як `DISCONT`. Вихід обробляє payload після розблокування. Це реалізація з копіюванням. Вимірювання пропускної здатності на цільовому відео ще попереду.

## Використання в ноді

1. Джерело після узгодження формату викликає `context.create_shm_generation(port_id, video=..., audio=[...], buffers={endpoint: (slots, slot_bytes)})`. По одному кільцю на потік. Передай фактичні `Gst.Caps` і структурні метадані за схемою. SDK перевіряє fixed raw caps, розмір канонічного відеобуфера та вирівнювання interleaved PCM.
2. Виклич `await generation.publish()`. SDK дочекається підтвердження runtime. Після цього для обов’язкового виходу можна оголосити `running`. `generation.write(endpoint_id, MediaFrame(data, pts, duration, dts=-1, flags=0))` повертає `False`, якщо кадр пропущено через зайнятий слот копіювання. Воркер має обліковувати ці втрати.
3. Споживач отримує `on_contract(local_port_id, contract)` після `start()`, відкриває `context.open_shm(contract)` і читає `reader.read(endpoint_id)`. Це один скопійований семпл або `None`. При `on_contract(..., None)` споживач закриває попередній reader і переходить в очікування. При новому поколінні він скидає стару чергу та перебудовує прив’язку часу. Callback обмежений п’ятьма секундами й має швидко встановлювати власні обробники, як `start()`.
4. При зміні формату зупини запис у старий об’єкт, підготуй новий і опублікуй його. SDK звільнить старе покоління після підтвердження. При втраті сигналу виклич `await generation.close()` для відкликання й перейди в `waiting_signal`. Runtime також відкликає контракти при виході, зупинці або переході з `running` до очікування. Пізній споживач отримує поточний snapshot. Перезапущений воркер отримує новий ID і новий snapshot без відновлення застарілої черги.

Час у кільці — running time джерела в наносекундах. Функція `gst_shm.from_gst_buffer()` переводить PTS/DTS через `TIME` segment зі швидкістю 1. `gst_shm.to_gst_buffer()` застосовує переданий споживачем спільний `base` для відео та аудіо. `duration` обов’язкова, відсутній DTS позначається `-1`. Код ноди має забезпечити канонічні системні буфери, нормалізувати нестандартні strides/offsets та передати потрібні ознаки полів. SHM не переносить GstMeta, GPU memory або багатоплощинний аудіолейаут; аудіо підтримується в interleaved PCM без перестановки каналів. У наступних SDI/SRT нодах потрібно перевірити спільну прив’язку до pipeline clock, компенсацію затримки й безперервність відтворення.

Керування часом спирається на [GStreamer TIME segment](https://gstreamer.freedesktop.org/documentation/gstreamer/gstsegment.html), а канонічні розміри — на [GstVideoInfo](https://gstreamer.freedesktop.org/documentation/video/video-info.html) і [GstAudioInfo](https://gstreamer.freedesktop.org/documentation/audio/audio-info.html).

## Ручне приймання на Linux

Виконай зі свіжого окремого checkout із системними Python GI/GStreamer і `python3-jsonschema`. Сценарій запускає приватний runtime та три воркери під поточним користувачем. Він копіює код і тестові модулі в тимчасову папку під `/dev/shm`, використовує власні конфіги, Unix socket та GStreamer registry й прибирає їх після завершення. Сценарій не використовує systemd-служби встановленого застосунку.

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src /usr/bin/python3 tests/linux_shm_acceptance.py
```

Сценарій перевіряє ранній старт одного виходу, пізнє підключення другого, спільне покоління, монотонні PTS, тривалість, збіг A/V timestamp і збереження двох різних PCM-каналів. Він навмисно сповільнює другий вихід, перевіряє його пропуски та прогрес першого після зупинки другого. Далі перезапускає джерело, перевіряє відкликання, підключення двох виходів до нового покоління й очищення SHM. Очікуваний результат — JSON з лічильниками й повідомлення `SHM fan-out acceptance passed`.

Сценарій підготовлено як вихідний код. Фактичний прогін Linux і вимірювання A/V drift, latency та пропускної здатності на реальних GStreamer-виходах залишаються окремим прийманням.
